# Discord 音樂 Bot

音樂功能屬於 `dsh-discord`。AudioUsbStudio 只提供唯讀的 yt-dlp、Node、FFmpeg、ffprobe 等工具引用，原始碼、設定、二進位檔均不修改，也不在該專案中寫入暫存或 Python bytecode。

## 使用

斜線指令的處理中提示與完成回覆會公開顯示於使用指令的頻道，所有具有該頻道閱覽權限的成員皆可看到。既有的指令執行權限仍由存取政策控制；回覆不觸發使用者、角色或全體標註通知。

先加入 Discord 語音頻道，再使用：

| 指令 | 用途 |
|---|---|
| `/play query:網址或關鍵詞` | 點歌並加入佇列 |
| `/music play query:網址或關鍵詞` | 相同功能的音樂命名空間版本 |
| `/music skip` | 跳過目前歌曲，包括還在下載或音量處理的歌曲 |
| `/music stop` | 停止音樂、取消預處理、清空佇列 |
| `/music pause`、`/music resume` | 暫停／繼續 |
| `/music queue`、`/music nowplaying` | 查看佇列／目前歌曲 |
| `/music status` | 查看 UDP／WebSocket 往返、目標／實際碼率、頻道上限、音訊預讀、來源缺口與 worker 延遲 |
| `/music volume percent:0–100` | 調整播放音量；預設 60%，100 為正規化後的基準音量 |
| `/music bitrate kbps:320` | 設定播放目標碼率，選項為 16、32、48、64、96、128、192、256、320、384 kbps；預設 128 |
| `/music bitrate` | 查詢目標碼率、實際輸出與頻道上限 |
| `/music channels count:2` | 選 1 單聲道或 2 雙聲道立體聲；320／384 kbps 須選 2 |
| `/music channels` | 查詢目前聲道、碼率與頻道上限 |
| `/music join`、`/music leave` | 加入／離開語音頻道 |

原本的 `/stop`、`/skip` 完整保留為 AI 任務控制，不攔截、不改名。原有 `/join`、`/next`、`/pause`、`/resume`、`/queue`、`/leave` 音樂別名仍可用。原本聊天與 AI Session 綁定方式保持不變。

操作播放、跳歌、停止、暫停、音量、碼率與離開時，使用者須在機器人目前所在的語音頻道。查詢佇列、目前歌曲與碼率不需要加入語音。機器人需要 Connect、Speak、文字回覆及應用程式指令權限。

碼率及聲道設定依伺服器分開，保留至離開語音（含閒置自動離開）或外掛重載；停止、跳歌及下一首沿用設定。播放中切換會從目前位置重建串流，可能短暫停頓，保留原本音量及播放／暫停狀態；失敗時恢復舊設定與串流。文字指令接受 `/music bitrate 16` 至 `/music bitrate 384` 的整數，以及 `/music channels 1` 或 `/music channels 2`。設定聲道須在機器人所在的語音頻道；查詢不需要加入語音。

實際碼率取目標、頻道設定與編碼上限的較低值（單聲道 256 kbps、雙聲道 384 kbps）。讀不到頻道設定時暫以 64 kbps 為上限。例如選擇雙聲道 320 kbps，但頻道設為 64 kbps，會明確顯示實際輸出 64 kbps；在 Discord 調整頻道後重新執行碼率指令即可重新套用。切回單聲道會將實際輸出限制在 256 kbps 以內，保留目標設定，切回雙聲道時可恢復。指令不修改 Discord 頻道設定。[Discord 頻道碼率說明](https://docs.discord.com/developers/resources/channel#modify-channel)列出各頻道及伺服器等級限制。

320 kbps 測試順序：`/music channels count:2` → `/music bitrate kbps:320` → `/music status`。確認狀態為「雙聲道立體聲」且實際音訊碼率為 320 kbps。恢復預設請用 `/music channels count:2` 與 `/music bitrate kbps:128`。Discord 輸出為重新編碼的 Opus，包含正規化與播放音量；不是來源 MP3／AAC 檔案的免轉碼直通。

## 聊天調用音樂（2026-10-24）

在聊天中 @機器人，直接說「幫我播放周杰倫的晴天」「下一首」「暫停音樂」「把音量設為35」即可讓 DSH 調用 `dsh_im_music`。機器人仍需正常獲准回覆這段聊天；原生斜線音樂指令維持原有存取流程。

也支援「把音樂關掉」「聲音小一點」「大聲一點」等口語操作。相對音量每次依目前音量增減 10 個百分點，最低 0%、最高 100%；明確指定百分比時則使用該數值。歌名與操作分開解析，例如 `播放 Don't Stop Me Now` 不會被歌名中的 `Don't` 攔截；「不要停，繼續播放」只處理繼續播放。

授權來自本次實際收到的發言。工具不能自行指定使用者、文字頻道或伺服器；引文、歷史記錄、程式範例與普通喜好敘述不會授予播放權限。私訊不提供音樂操作；更動播放器仍要求發話者在對應語音頻道。每次聊天最多提交四項不同操作，相同操作不重複執行。歌曲準備成功提交後獨立於聊天回合運行；請求結束會撤銷尚未執行的工具權限。

明確音樂要求直接調用播放器，不先讀聊天歷史。點歌只接受關鍵詞或 HTTP(S) 連結；聊天工具不提供本機音訊路徑。DSH 必須根據工具回傳的成功、準備中或錯誤狀態回答，不能把加入佇列說成已經聽得到音樂。音訊預設目標為 **128 kbps、雙聲道**；頻道設為 64 kbps 時，實際輸出仍為 64 kbps。

## 指令處理順序與隔離

音樂播放器與 AI 對話分別處理；一般 @ 對話再多，也不能把已辨識的音樂指令合併為模型提示、插話、批次輸入或互動回答。

| 處理階段／類型 | 順序與行為 | 作用範圍 |
| --- | --- | --- |
| 接收與去重 | 先忽略機器人自身、重複訊息及重複互動；文字群聊仍須符合原有喚醒條件 | 原始頻道或討論串 |
| 原生指令確認 | 音樂指令先保留位置，再確認 Discord 互動；確認完成前不操作播放器，確認失敗即釋放工作 | 每個互動自己的公開回覆 |
| `/music stop`、`/music leave` | 通過語音權限檢查後，取消較早、尚未完成的音樂操作，停止歌曲準備與預處理；較晚的新點歌仍可執行 | 同一伺服器的播放器，含不同文字頻道 |
| `/play`、join、skip、pause、resume、volume、bitrate 設定 | 進入音樂專用佇列，按接收位置依序改動播放器；skip 取消目前歌曲後繼續下一首 | 每個伺服器獨立 |
| `/music queue`、nowplaying、status、bitrate 查詢 | 完成互動確認後讀取當前快照，不等待下載、連線或一般聊天工作 | 對應伺服器的當前狀態 |
| AI `/stop`、`/skip` | 使用與文字對話相同的 `group:頻道`／`direct:頻道` Session 鍵，直接控制 AI，不進入音樂佇列 | 指令所在的對話；討論串不導向父頻道 |
| 其他管理指令 | 保留既有執行權限及處理流程 | 對應 AI 對話 |
| 一般 @ 對話 | Discord 採逐則 FIFO：先保留接收順序，再處理歷史與路由；停用自動合併、擁有者／追問插隊與自動插話，必要時明確使用 `/steer` | 每個 AI 對話獨立，與播放器分開；其他渠道維持原排程 |

音樂對伺服器成員開放，文字與原生指令採相同原則；會改動播放器的操作仍須通過語音頻道檢查。AI 的白名單、聊天靜音與使用者暫停不會被音樂操作修改，也不會用來取消播放器。帶有圖片／附件或不接受參數的控制指令夾帶額外文字時，會本機提示修正，不轉交模型或意外執行控制動作。

重載會取消舊音樂管理器的工作。過期回呼持有舊實例，無法接觸新版播放器；取消後才返回的來源會被釋放，不能重新開播。每個互動只更新自己的回覆，過長內容會截短，取消也會完成提示。

對話順序的修正包含兩個層次：同一來源頻道的歷史讀取與路由只能依序准入，但不等待整個模型回答才准入下一則；進入實際對話佇列後，按准入順序完成各回合。排隊提示屬狀態通知，與模型的正式回答分開。不同頻道或討論串之間可以並行，沒有跨頻道的全域回答順序。

這裡保障指令的執行與隔離。公開訊息仍按 Discord 的時間順序顯示，後續聊天會讓畫面正常向下捲動，不會自動置頂或重貼音樂訊息。

## 選歌與播放

- YouTube 單曲網址經主機名及影片 ID 驗證後直接使用。
- Bilibili BV／av 影片及 au 音訊直接下載原站音軌；b23 分享連結解析為支援的原站連結後走相同流程，不經 YouTube 搜尋或 DSH 選歌。移除追蹤參數，保留 `p`，未指定時固定第一 P；不同分 P 使用不同快取。擷取沿用本機 yt-dlp 及 `tools/ytdlp-plugins` 相容擷取器。
- 關鍵詞先取得最多五個真實 YouTube 候選，再交由 DSH 選擇最符合的版本。其他網頁會先嘗試取得曲名，再走同一個搜尋及 DSH 流程。
- DSH 只接受候選清單中的影片 ID，不能回傳任意執行命令或自行捏造下載網址。選歌使用獨立 Session；停止音樂只取消音樂工作，不操作聊天的 AI 任務。
- 音樂選歌 Session 的工作目錄固定在本專案 `.dsh-im/music/dsh-workspace`。生產環境的 bot-scoped `createSession()` 會強制套用聊天工作區，因此此功能使用既有公開 `session.create` RPC 的 `cwd` 模式建立獨立工作區。沒有更動共用的聊天工作區邏輯。
- DSH 選歌逾時為十秒；無效結果或服務暫時不可用時，改用已驗證的搜尋首選，並在播放通知中說明。每個 Session 最多選歌八次，避免累積很長的提示歷史。
- 先完整下載並量測音量，再以整首固定的線性增益調整至約 −20 LUFS，峰值保留 3 dB 餘量；不使用會壓縮原曲動態的自動增益回退。高動態曲目若須優先限制峰值，會比目標更安靜。正規化快取改為 48 kHz、24-bit 雙聲道 FLAC；實際播放由 FFmpeg 子程序套用預設 60% 音量並按所選聲道與碼率編碼。快取版本為 3，不沿用舊 128 kbps Opus 快取；首次重播會重新處理，無損快取較大，仍沿用原有容量及期限清理規則。
- 網站僅回傳試聽或截短音訊時，會比較音訊時長並拒絕播放。直播與超過三十分鐘的音訊會回報限制。
- 支援既有本機音訊檔及公開音訊直連；同樣先處理音量。一般網頁不會直接當成音訊傳給播放器；受限、無法辨識或會重新導向的網頁可能需要改用歌曲關鍵詞。

## 效能與穩定性

- Discord 音樂用戶端、語音連線、播放器、20 ms 發送時鐘、重連與音訊處理生命週期均由專用 Node worker 執行。主程序只轉交指令、DSH 選歌和通知；音訊封包不經過主程序。worker 首次收到音樂指令才建立，卸載外掛時先取消工作及關閉資源，再終止 worker；意外退出時，未完成指令會失敗，下次指令重新建立 worker，舊佇列不會自動重播。
- `/music status` 顯示「播放執行：獨立 worker」及 worker 自己的最大延遲。「音訊預讀」代表已備妥的音訊時長，不是端到端延遲；既有 `bufferedMs` 日誌欄位保持相同意義，`execution` 區分 `worker`／`main`。主程序阻塞期間已開始的播放可以繼續，但新指令、通知與 DSH 選歌仍需等待主程序恢復；整機 CPU 飽和及外部網路問題仍可能影響播放。
- 每個 Discord 伺服器各自管理播放器、音量及最多 25 首待播歌曲。
- 預處理下一首；相同歌曲共用處理工作與正規化音訊，快取不會重複下載或轉檔。
- 正規化快取最多 64 首、512 MB、保留一天；正在使用的檔案不會被回收。檔案放在 `.dsh-im/music/`。
- 同時最多兩個下載／正規化工作。網路操作、子程序、DSH 選歌及語音 Ready 等待都有期限。
- 跳歌、停止、離開會取消相應工作；若另一個伺服器也在使用同一處理工作，單一使用者的取消不會中斷其他使用者。
- 語音斷線會嘗試恢復；失敗時清除佇列並通知。沒有待播歌曲三分鐘後自動離開。
- 使用套件原有的 `@discordjs/voice`、DAVE 與 Opus 支援；沒有新增外部 AI 服務或複製 API 金鑰／Discord Token。

### 播放卡頓與 UDP 保護

- 開播前預先準備約 480 ms 的 Opus 封包；讀寫各有 48 幀的有界緩衝。Discord 原有的 20 ms 發送時鐘保持不變，沒有加快或成批重送 UDP 音訊。
- 解碼、音量與 Opus 編碼由 FFmpeg 子程序執行，可選單／雙聲道，使用固定碼率、最低編碼複雜度與單執行緒。worker 分離 Ogg／Opus 並傳送封包，兩層資源都停用 `inlineVolume`，不在 DSH 主程序內使用 JavaScript／WASM 即時重編碼。
- 播放目標預設為 128 kbps 雙聲道，可用 `/music channels` 及 `/music bitrate` 設定雙聲道最高 384 kbps；較低的頻道碼率仍會限制實際輸出。128 kbps 的 20 ms 固定碼率音訊負載為每幀 320 bytes；UDP、加密與協議標頭仍有額外流量。48 kHz 與 20 ms 幀長保留供 Discord 播放。
- 音量仍預設 60%，正規化目標維持 −20 LUFS。`/music volume` 會短暫暫停、從目前播放位置重建 FFmpeg 串流，再恢復原有播放／暫停狀態；可能有短暫停頓及數十毫秒的定位誤差。跳歌／停止會銷毀緩衝及終止子程序，較晚的舊資源事件不能中止新串流。
- 短暫斷線時先暫停讀取歌曲、保留資源與佇列，等待庫本身恢復，再最多重試三次；成功後從目前位置續播。停止／離開會取消重連。Discord 4014 踢出或權限撤銷情況不會強制重新加入。
- 每十秒記錄一次安全的健康統計，僅在進入異常或明確恢復時發出狀態變化通知。統計包含 UDP／WebSocket ping、相鄰 UDP ping 差異、主程序最大延遲、來源缺包及緩衝長度，不記錄語音端點、Token、DAVE 金鑰或私人內容。
- UDP ping 是保活往返，不是接收端 RTP 丟包率。目前沒有外部語音接收端的丟包統計；本機緩衝也不能讓被主程序阻塞的發送時鐘繼續運作。這些數據用來區分主機排程、音訊供應與外部連線問題。

可執行 `node scripts/smoke-music-transport.mjs`，以真正的 Opus 編碼與播放器時鐘進行本機 UDP 回送檢查，不會登入或向 Discord 發送訊息。

先前 32 kbps 版本的歷史驗證：**79/79 測試通過**，另涵蓋真實 32 kbps 單聲道 CBR 輸出、音量與接續位置、子程序取消、音量重建失敗回復及延後就緒的暫停資源。既有 @ 對話 FIFO、12 則訊息積壓、指令排序、取消及重載測試仍保留。新版八秒本機測試送出、收到及回送各 406 個封包，零本機丟包、零來源缺口；送包間隔 P95 為 32.07 ms、最大 32.66 ms，UDP 回送 P95 為 0.39 ms，主程序延遲 P99 為 16.86 ms、最大 17.04 ms。這是單次本機量測，不能當作 Discord 外部線路已穩定的證明，也不能與不同負載下的運行紀錄直接比較。重新載入後，實際播放約三十秒再查 `/music status`，目標應顯示 128 kbps、FFmpeg 子程序與雙聲道；實際輸出仍取決於頻道上限，才能確認新版設定生效。
