# Discord 音樂 Bot

音樂功能屬於 `dsh-discord`。AudioUsbStudio 只提供唯讀的 yt-dlp、Node、FFmpeg、ffprobe 等工具引用，原始碼、設定、二進位檔均不修改，也不在該專案中寫入暫存或 Python bytecode。

## 使用

斜線指令的處理中提示與完成回覆會公開顯示於使用指令的頻道，所有具有該頻道閱覽權限的成員皆可看到。既有的指令執行權限仍由存取政策控制；回覆不觸發使用者、角色或全體標註通知。

先加入 Discord 語音頻道，再使用：

| 指令 | 用途 |
|---|---|
| `/play query:網址或關鍵詞` | 點歌並加入佇列 |
| `/music play query:網址或關鍵詞` | 相同功能的音樂命名空間版本 |
| `/music skip` | 跳過目前歌曲，包括還在下載或音量處理的歌曲 |
| `/music stop` | 停止音樂、取消預處理、清空佇列 |
| `/music pause`、`/music resume` | 暫停／繼續 |
| `/music queue`、`/music nowplaying` | 查看佇列／目前歌曲 |
| `/music status` | 查看 UDP／WebSocket 往返、碼率、封包緩衝、來源缺口與主程序延遲 |
| `/music volume percent:0–100` | 調整播放音量；預設 60%，100 為正規化後的基準音量 |
| `/music join`、`/music leave` | 加入／離開語音頻道 |

原本的 `/stop`、`/skip` 完整保留為 AI 任務控制，不攔截、不改名。原有 `/join`、`/next`、`/pause`、`/resume`、`/queue`、`/leave` 音樂別名仍可用。原本聊天與 AI Session 綁定方式保持不變。

操作播放、跳歌、停止、暫停、音量與離開時，使用者須在機器人目前所在的語音頻道。查詢佇列與目前歌曲不需要加入語音。機器人需要 Connect、Speak、文字回覆及應用程式指令權限。

## 指令處理順序與隔離

音樂播放器與 AI 對話分別處理；一般 @ 對話再多，也不能把已辨識的音樂指令合併為模型提示、插話、批次輸入或互動回答。

| 處理階段／類型 | 順序與行為 | 作用範圍 |
| --- | --- | --- |
| 接收與去重 | 先忽略機器人自身、重複訊息及重複互動；文字群聊仍須符合原有喚醒條件 | 原始頻道或討論串 |
| 原生指令確認 | 音樂指令先保留位置，再確認 Discord 互動；確認完成前不操作播放器，確認失敗即釋放工作 | 每個互動自己的公開回覆 |
| `/music stop`、`/music leave` | 通過語音權限檢查後，取消較早、尚未完成的音樂操作，停止歌曲準備與預處理；較晚的新點歌仍可執行 | 同一伺服器的播放器，含不同文字頻道 |
| `/play`、join、skip、pause、resume、volume | 進入音樂專用佇列，按接收位置依序改動播放器；skip 取消目前歌曲後繼續下一首 | 每個伺服器獨立 |
| `/music queue`、nowplaying、status | 完成互動確認後讀取當前快照，不等待下載、連線或一般聊天工作 | 對應伺服器的當前狀態 |
| AI `/stop`、`/skip` | 使用與文字對話相同的 `group:頻道`／`direct:頻道` Session 鍵，直接控制 AI，不進入音樂佇列 | 指令所在的對話；討論串不導向父頻道 |
| 其他管理指令 | 保留既有執行權限及處理流程 | 對應 AI 對話 |
| 一般 @ 對話 | Discord 採逐則 FIFO：先保留接收順序，再處理歷史與路由；停用自動合併、擁有者／追問插隊與自動插話，必要時明確使用 `/steer` | 每個 AI 對話獨立，與播放器分開；其他渠道維持原排程 |

音樂對伺服器成員開放，文字與原生指令採相同原則；會改動播放器的操作仍須通過語音頻道檢查。AI 的白名單、聊天靜音與使用者暫停不會被音樂操作修改，也不會用來取消播放器。帶有圖片／附件或不接受參數的控制指令夾帶額外文字時，會本機提示修正，不轉交模型或意外執行控制動作。

重載會取消舊音樂管理器的工作。過期回呼持有舊實例，無法接觸新版播放器；取消後才返回的來源會被釋放，不能重新開播。每個互動只更新自己的回覆，過長內容會截短，取消也會完成提示。

對話順序的修正包含兩個層次：同一來源頻道的歷史讀取與路由只能依序准入，但不等待整個模型回答才准入下一則；進入實際對話佇列後，按准入順序完成各回合。排隊提示屬狀態通知，與模型的正式回答分開。不同頻道或討論串之間可以並行，沒有跨頻道的全域回答順序。

這裡保障指令的執行與隔離。公開訊息仍按 Discord 的時間順序顯示，後續聊天會讓畫面正常向下捲動，不會自動置頂或重貼音樂訊息。

## 選歌與播放

- YouTube 單曲網址經主機名及影片 ID 驗證後直接使用。
- 關鍵詞先取得最多五個真實 YouTube 候選，再交由 DSH 選擇最符合的版本。其他網頁會先嘗試取得曲名，再走同一個搜尋及 DSH 流程。
- DSH 只接受候選清單中的影片 ID，不能回傳任意執行命令或自行捏造下載網址。選歌使用獨立 Session；停止音樂只取消音樂工作，不操作聊天的 AI 任務。
- 音樂選歌 Session 的工作目錄固定在本專案 `.dsh-im/music/dsh-workspace`。生產環境的 bot-scoped `createSession()` 會強制套用聊天工作區，因此此功能使用既有公開 `session.create` RPC 的 `cwd` 模式建立獨立工作區。沒有更動共用的聊天工作區邏輯。
- DSH 選歌逾時為十秒；無效結果或服務暫時不可用時，改用已驗證的搜尋首選，並在播放通知中說明。每個 Session 最多選歌八次，避免累積很長的提示歷史。
- 先完整下載並量測音量，再以整首固定的線性增益調整至約 −20 LUFS，峰值保留 3 dB 餘量；不使用會壓縮原曲動態的自動增益回退。高動態曲目若須優先限制峰值，會比目標更安靜。正規化快取保留 48 kHz 雙聲道 Opus；實際播放由 FFmpeg 子程序套用預設 60% 音量並轉為 32 kbps 單聲道。
- 網站僅回傳試聽或截短音訊時，會比較音訊時長並拒絕播放。直播與超過三十分鐘的音訊會回報限制。
- 支援既有本機音訊檔及公開音訊直連；同樣先處理音量。一般網頁不會直接當成音訊傳給播放器；受限、無法辨識或會重新導向的網頁可能需要改用歌曲關鍵詞。

## 效能與穩定性

- 每個 Discord 伺服器各自管理播放器、音量及最多 25 首待播歌曲。
- 預處理下一首；相同歌曲共用處理工作與正規化音訊，快取不會重複下載或轉檔。
- 正規化快取最多 64 首、512 MB、保留一天；正在使用的檔案不會被回收。檔案放在 `.dsh-im/music/`。
- 同時最多兩個下載／正規化工作。網路操作、子程序、DSH 選歌及語音 Ready 等待都有期限。
- 跳歌、停止、離開會取消相應工作；若另一個伺服器也在使用同一處理工作，單一使用者的取消不會中斷其他使用者。
- 語音斷線會嘗試恢復；失敗時清除佇列並通知。沒有待播歌曲三分鐘後自動離開。
- 使用套件原有的 `@discordjs/voice`、DAVE 與 Opus 支援；沒有新增外部 AI 服務或複製 API 金鑰／Discord Token。

### 播放卡頓與 UDP 保護

- 開播前預先準備約 480 ms 的 Opus 封包；讀寫各有 48 幀的有界緩衝。Discord 原有的 20 ms 發送時鐘保持不變，沒有加快或成批重送 UDP 音訊。
- 解碼、音量與 Opus 編碼移至 FFmpeg 子程序，使用單聲道、固定碼率、最低編碼複雜度與單執行緒。主程序僅分離 Ogg／Opus 並傳送封包，兩層資源都停用 `inlineVolume`，不再於 DSH 主程序內使用 JavaScript／WASM 即時重編碼。
- 播放目標為 32 kbps；較低的頻道碼率仍會限制實際輸出。相較先前實際使用的 64 kbps，音訊封包負載減半；UDP、加密與協議標頭仍有額外流量。48 kHz 與 20 ms 幀長保留供 Discord 播放。
- 音量仍預設 60%，正規化目標維持 −20 LUFS。`/music volume` 會短暫暫停、從目前播放位置重建 FFmpeg 串流，再恢復原有播放／暫停狀態；可能有短暫停頓及數十毫秒的定位誤差。跳歌／停止會銷毀緩衝及終止子程序，較晚的舊資源事件不能中止新串流。
- 短暫斷線時先暫停讀取歌曲、保留資源與佇列，等待庫本身恢復，再最多重試三次；成功後從目前位置續播。停止／離開會取消重連。Discord 4014 踢出或權限撤銷情況不會強制重新加入。
- 每十秒記錄一次安全的健康統計，僅在進入異常或明確恢復時發出狀態變化通知。統計包含 UDP／WebSocket ping、相鄰 UDP ping 差異、主程序最大延遲、來源缺包及緩衝長度，不記錄語音端點、Token、DAVE 金鑰或私人內容。
- UDP ping 是保活往返，不是接收端 RTP 丟包率。目前沒有外部語音接收端的丟包統計；本機緩衝也不能讓被主程序阻塞的發送時鐘繼續運作。這些數據用來區分主機排程、音訊供應與外部連線問題。

可執行 `node scripts/smoke-music-transport.mjs`，以真正的 Opus 編碼與播放器時鐘進行本機 UDP 回送檢查，不會登入或向 Discord 發送訊息。

本次 **79/79 測試通過**，另涵蓋真實 32 kbps 單聲道 CBR 輸出、音量與接續位置、子程序取消、音量重建失敗回復及延後就緒的暫停資源。既有 @ 對話 FIFO、12 則訊息積壓、指令排序、取消及重載測試仍保留。新版八秒本機測試送出、收到及回送各 406 個封包，零本機丟包、零來源缺口；送包間隔 P95 為 32.07 ms、最大 32.66 ms，UDP 回送 P95 為 0.39 ms，主程序延遲 P99 為 16.86 ms、最大 17.04 ms。這是單次本機量測，不能當作 Discord 外部線路已穩定的證明，也不能與不同負載下的運行紀錄直接比較。重新載入後，實際播放約三十秒再查 `/music status`，應顯示 32 kbps、FFmpeg 子程序與單聲道，才能確認新版設定生效。

## 驗證與載入

```powershell
npm run test:music
node scripts/smoke-music-audio.mjs 'https://www.youtube.com/watch?v=jNQXAC9IVRw'
```

手動音訊檢查會實際下載、處理、量測音量，並產生 Discord 可用的 Opus 封包；不會登入 Discord、不會發送訊息，也不會呼叫真正的 DSH 模型。DSH 選歌及語音狀態測試使用可控的測試介面，不能代替真實伺服器中的語音驗收。

本機外掛已透過 `scripts/build-local.mjs` 重建 `lib/index.js`、`lib/client.js`。既有 DSH 程序仍持有舊模組時，請重新載入此外掛或重新啟動 DSH；Discord READY 流程會沿用原機制註冊指令，不會另外建立重複的全域指令。實際伺服器中應再驗證 `/play`、`/music skip`、`/music stop`，並確認原 `/skip`、`/stop` 仍控制 AI。

參考：[FFmpeg loudnorm](https://ffmpeg.org/ffmpeg-filters.html#loudnorm)、[discord.js voice](https://discord.js.org/docs/packages/voice/0.19.2)、[yt-dlp](https://github.com/yt-dlp/yt-dlp)。

## 本機驗證紀錄（2026-10-24）

### 較低音量設定

收到失真與音量過大的回饋後，預設播放增益由 100% 降至 60%，正規化目標由 −16 LUFS 改為 −20 LUFS，真峰值目標由 −1.5 dB 改為 −3 dB。改用量測後的整首固定增益，保留動態範圍。快取版本升至 2，下一次點歌會重新處理，不會沿用較響的舊快取；沒有刪除舊音訊檔。

這些修改降低輸出電平與動態處理，不能修復來源本身已存在的失真，是否改善仍須真實語音頻道試聽。當下仍使用舊外掛播放時，可先透過 `/music volume percent:40` 即時降低音量；重新載入外掛後預設為 60%。

本次調整後 **30/30 測試通過**。以回報時的本機快取音訊作單次對照：原始快取為 −16.01 LUFS，線性調整後為 −20.00 LUFS；套用 60% 增益並經真正的 Discord Opus 編碼／解碼後，量得 −24.46 LUFS、真峰值 −12.72 dB，16-bit PCM 沒有飽和削波樣本。相較原先約低 8.45 dB。這是本機音訊鏈路量測，不等同於已確認真實頻道的聽感或網路品質。

### 被動監測

`npm run monitor:music` 會增量讀取本機 `.dsh/logs/dsh-discord.log`，在本專案 `.dsh-im/music-monitor/` 儲存游標及已回報事件。輸出僅含時間、事件分類、計數及驗證狀態，不輸出原始訊息、網址、Token 或使用者／伺服器 ID。重複檢查沒有新事件時不產生通知。

監測涵蓋指令同步、實際指令處理、DSH 選歌是否進入播放流程、音訊提交播放器，以及下載、音量處理、語音／Gateway 錯誤。`music.playing` 日誌代表音訊已交給播放器，不能單獨證明語音頻道中的使用者已經聽見音樂。監測不登入 Discord、不發送訊息，也不改動運行中的外掛或 AudioUsbStudio。

- 初版音樂測試 **19/19 通過**，含真正的 Discord 橋接分流、獨立選歌 Session、下載中跳歌／停止、預處理取消、語音 Ready 失敗、舊播放器事件、快取共用與音量處理。以下 −16 LUFS 數值是調低音量前的初版紀錄。
- 兩個不同原始音量的測試訊號，轉換後均接近 −16 LUFS，彼此音量差小於 0.3 LU。
- 真實 YouTube `jNQXAC9IVRw` 完整下載及音量處理通過：19.1065 秒、−15.74 LUFS、950 個可解碼及重編碼的 Discord Opus 封包。首次音訊檢查約 4.6 秒；這是單次本機量測，不是延遲保證。
- 關鍵詞搜尋能取得該影片，並重用已正規化音訊；此線上測試的候選選擇介面使用固定測試回覆，沒有冒稱呼叫真正的 DSH 模型。
- AudioUsbStudio 的 Git 狀態、既有未提交差異與唯讀引用工具 SHA-256 均和實作前快照相同。原 AI `control-command.mjs` 沒有改動。
- `lib/index.js`、`lib/client.js` 已重建。真正的 DSH 模型選歌、Discord 指令同步及語音頻道播音仍須在重新載入外掛後驗收；本次沒有讀取或輸出 Token，也沒有自動向真實頻道發送測試訊息。

### 「正在思考」停住的修正

2026-10-24 的真實紀錄出現 `interaction acknowledgement failed`，原因為互動確認回應沒有可解析的 JSON；程式在確認步驟就返回，沒有繼續執行音樂指令。互動 callback 現在依其無回應本文的契約處理成功結果，不影響其他 REST 端點的 JSON 驗證，也不忽略權限錯誤。
